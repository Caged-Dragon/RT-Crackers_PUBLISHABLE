# Upgrade V3 (U21 - U40): deterministic, auditable, business-rule-driven

A **migration** on top of base + upgrade v2. Base module files are untouched.

## How to deploy
1. base: `build/rt_crackers_full.sql`, then v2: `build/rt_crackers_upgrade_v2_full.sql`
2. V3, psql from the database root: `psql "$DATABASE_URL" -f 99_DEPLOYMENT/007_Upgrade_v3_build.sql`
   or Supabase SQL editor: paste `build/rt_crackers_upgrade_v3_full.sql` (generated by `build/build_upgrade_v3.sh`)
- Take a backup / snapshot first. One transaction: any error rolls everything back. It refuses to run twice.

## READ THIS FIRST: existing numbers change (U21)
Orders, invoices, returns, replacements, COD receipts and referral codes that already exist are **renumbered**
(e.g. `RTC261003000001` becomes `ORD2026000001`). If those numbers were already sent to customers, keep a copy of the old ones before running.
Products keep their SKU; admins may still type their own SKU or coupon code, the generated code is used only when none is given.

## Things to know
- Old CHAR status / gender columns stay and are kept in sync with the new `*_id` columns, so existing code keeps working.
- Address types: v2 had already replaced `address_type` with `address_label`, so `address_types` uses HOME / OFFICE / WAREHOUSE / OTHER and `addresses.address_label` references it.
- `country`/`city` in `audit_logs` need a geo-IP lookup in your application; the database cannot guess them.
- Set per request: `SET LOCAL app.current_user_id = '<users.user_id>'` (ownership, versions, audit); admins use `app.current_admin_id`.
- After every upgrade run `SELECT * FROM v_missing_fk_indexes;` and `SELECT * FROM v_undocumented_tables;`.
- `database_metadata.owner` holds team names I chose (Security & Access, Finance, Logistics, ...). Rename them to your real teams.
